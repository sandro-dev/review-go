# **11.5: Comunicação entre Goroutines com Channels**

Até agora, aprendemos a iniciar goroutines para executar tarefas concorrentemente e a usar `WaitGroup` para esperar que elas terminem. Mas como fazemos para que essas goroutines **conversem entre si**? Como uma goroutine pode enviar um resultado de forma segura para outra? A resposta idiomática em Go são os **Channels**.

## 1\. O Problema: Compartilhamento de Memória é Complicado

A aula começa tentando resolver um problema de uma forma que é comum em outras linguagens: uma goroutine modifica uma variável (uma lista/slice) e a outra a lê, usando um ponteiro para compartilhar o mesmo espaço de memória.

```go
// Abordagem inicial (problemática)
var lista []int
go func() {
    // Goroutine 1: Tenta popular a lista
    // ... append
}()
// Goroutine 2 (main): Tenta ler a lista
// ... for range
```

Como vimos, sem uma sincronização explícita (como `WaitGroup`), essa abordagem falha. A goroutine `main` provavelmente tentará ler a lista antes que a outra goroutine tenha tido tempo de populá-la. Mesmo com um `WaitGroup`, ainda poderíamos ter condições de corrida se múltiplas goroutines estivessem escrevendo na lista ao mesmo tempo.

Essa abordagem segue o padrão de **comunicar compartilhando memória**, que geralmente requer o uso de `Mutexes` para ser segura.

## 2\. A Solução "Go Way": Channels - Comunicar para Compartilhar

Go incentiva uma filosofia diferente: **"Não se comunique compartilhando memória; em vez disso, compartilhe memória comunicando-se."**

Um **channel** (canal) é a principal ferramenta para isso. Pense nele como um "túnel" ou "esteira transportadora" tipada, conectando duas ou mais goroutines.

  * Uma goroutine pode colocar um valor na esteira (**enviar**).
  * Outra goroutine pode pegar o valor na outra ponta (**receber**).

Essa comunicação é, por padrão, **sincronizada e segura**, eliminando a necessidade de locks manuais na maioria dos casos.

## 3\. Anatomia de um Channel

### a) Criação

Criamos um channel usando a função `make`, especificando o tipo de dado que ele transportará.

**Sintaxe:** `make(chan Tipo)`

```go
// Cria um canal que só pode transportar valores do tipo 'int'.
ch := make(chan int)
```

### b) Enviando e Recebendo Dados

A sintaxe usa o operador de seta `<-`. A direção da seta indica o fluxo dos dados.

  * **Enviar (Escrever):** `channel <- valor`

      * O valor flui *para dentro* do canal.
      * **Analogia:** A seta aponta para o canal.

    <!-- end list -->

    ```go
    ch <- 10 // Envia o valor 10 para o canal 'ch'.
    ```

  * **Receber (Ler):** `variavel := <-channel`

      * O valor flui *para fora* do canal.
      * **Analogia:** A seta "sai" do canal.

    <!-- end list -->

    ```go
    valor := <-ch // Espera um valor chegar no canal 'ch' e o armazena em 'valor'.
    ```

## 4\. O Poder da Sincronização: O Bloqueio (Blocking)

Por padrão, os channels são **não-bufferizados (unbuffered)**. Isso significa que eles têm um poder de sincronização intrínseco:

  * Uma operação de **envio (`ch <- ...`) bloqueará** a goroutine que a está executando até que outra goroutine esteja pronta para **receber** daquele canal.
  * Uma operação de **recebimento (`<- ch`) bloqueará** a goroutine até que outra goroutine **envie** um valor para aquele canal.

Esse comportamento de bloqueio é a "mágica" que garante a sincronização. É uma troca de bastão: o envio e o recebimento acontecem no mesmo instante.

## 5\. Exemplo Prático: Reescrevendo o Problema com Channels

Vamos aplicar esses conceitos para resolver o problema da aula de forma idiomática.

```go
package main

import "fmt"

// A função 'produtora' agora recebe um canal apenas para escrita (chan<- int).
func setList(ch chan<- int) {
	// 1. Após terminar o loop, a goroutine fecha o canal para sinalizar que
	//    não enviará mais valores.
	defer close(ch)

	for i := 0; i < 100; i++ {
		// 2. Envia cada número para o canal. A execução bloqueará aqui
		//    até que a goroutine principal esteja pronta para ler.
		ch <- i
	}
	fmt.Println("Produtor terminou de enviar.")
}

func main() {
	// 1. Cria o canal.
	ch := make(chan int)

	// 2. Inicia a goroutine 'produtora' de forma concorrente.
	go setList(ch)

	// 3. A goroutine 'consumidora' (main) usa um for...range para ler do canal.
	//    Este loop irá ler todos os valores que chegarem até que o canal seja fechado.
	for valor := range ch {
		fmt.Println("Recebido:", valor)
	}

	fmt.Println("Canal foi fechado. Fim do programa.")
}
```

## 6\. O `for...range` e a Necessidade do `close()`

  * **`for valor := range ch`:** Esta é a forma mais elegante de consumir dados de um channel. O laço automaticamente recebe valores do canal um por um e só termina quando o canal é **fechado**.
  * **`close(ch)`:** Como a aula demonstrou, se o produtor nunca fechar o canal, o `for...range` na goroutine `main` ficará esperando para sempre por mais um valor. Quando todas as outras goroutines terminam e a `main` ainda está bloqueada esperando, o runtime do Go detecta que não há mais esperança de progresso e lança um erro de **deadlock**.

**Regra de Ouro:** O `close` deve ser sempre chamado pelo **remetente (produtor)** para sinalizar ao(s) receptor(es) (consumidor(es)) que não há mais dados a caminho.

Esta aula demonstra como os channels simplificam drasticamente a comunicação segura entre goroutines, um problema que em muitas outras linguagens exigiria código complexo com locks, mutexes e variáveis de condição.
