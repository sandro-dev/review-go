# **11.6: Tópicos Avançados de Channels**

Nesta aula, exploramos funcionalidades mais avançadas dos channels que nos dão maior controle sobre o fluxo de dados, melhoram a segurança do nosso código e oferecem diferentes estratégias de sincronização.

## 1\. Channels Direcionais: Aumentando a Segurança e a Clareza

Go nos permite especificar, na assinatura de uma função, se um channel será usado apenas para **enviar** dados ou apenas para **receber** dados. Isso funciona como uma "guarda de trânsito", prevenindo erros e tornando a intenção do código explícita.

  * **Channel de Envio (Send-Only):** `chan<- T`

      * A seta "aponta para" o channel. Significa que, dentro da função, você só pode enviar dados para este canal.
      * **Uso:** Ideal para funções "produtoras".

  * **Channel de Recebimento (Receive-Only):** `<-chan T`

      * A seta "sai de" o channel. Significa que, dentro da função, você só pode receber dados deste canal.
      * **Uso:** Ideal para funções "consumidoras".

**Exemplo Prático (Refatorando a Aula Anterior):**

```go
package main

import "fmt"

// setList agora declara que 'ch' é um canal APENAS PARA ESCRITA (send-only).
func setList(ch chan<- int) {
	defer close(ch)
	for i := 0; i < 5; i++ {
		fmt.Println("Enviando:", i)
		ch <- i
		// A linha abaixo causaria um ERRO DE COMPILAÇÃO:
		// valor := <-ch // Erro: invalid operation: cannot receive from send-only channel ch
	}
}

// exibeLista poderia ser refatorada para aceitar um canal APENAS PARA LEITURA (receive-only).
func exibeLista(ch <-chan int) {
	for valor := range ch {
		fmt.Println("Recebido:", valor)
	}
}

func main() {
	ch := make(chan int)
	go setList(ch)
	exibeLista(ch)
}
```

**Por que isso é útil?**
Isso cria um contrato mais forte. Quando outro desenvolvedor lê a assinatura `func setList(ch chan<- int)`, ele sabe imediatamente, sem precisar ler o corpo da função, que esta função *não irá* ler dados do canal, apenas escrever. Isso previne bugs e torna a arquitetura do sistema mais clara.

## 2\. Visualizando a Sincronização de Channels Não-Bufferizados

A aula demonstra de forma brilhante o comportamento de bloqueio dos channels padrão (não-bufferizados). Eles forçam uma sincronização "casada" entre o remetente e o receptor.

  * A goroutine que **envia** (`ch <- i`) **para e espera** até que outra goroutine esteja pronta para **receber**.
  * A goroutine que **recebe** (`<- ch`) **para e espera** até que outra goroutine **envie** um valor.

O exemplo da aula com `time.Sleep` torna isso visível:

```go
// ...
func setList(ch chan<- int) {
    defer close(ch)
    for i := 0; i < 5; i++ {
        fmt.Println("Enviando:", i)
        ch <- i // Bloqueia aqui até que a 'main' leia o valor
    }
}

func main() {
    ch := make(chan int)
    go setList(ch)
    for valor := range ch {
        fmt.Println("Recebido:", valor)
        time.Sleep(1 * time.Second) // Simula um trabalho demorado do consumidor
    }
}
```

**Saída (com pausas de 1 segundo):**

```
Enviando: 0
Recebido: 0
Enviando: 1
Recebido: 1
Enviando: 2
Recebido: 2
...
```

A saída prova o comportamento de "troca de bastão". O produtor envia `0` e espera. O consumidor recebe `0`, processa por um segundo, e só então volta para receber `1`, desbloqueando o produtor para que ele possa enviar `1` e bloquear novamente.

## 3\. Channels com Buffer: Desacoplando o Produtor e o Consumidor

E se não quisermos que o produtor espere pelo consumidor a cada item? E se quisermos que o produtor possa "despejar" uma certa quantidade de itens e seguir em frente? Para isso, usamos **channels com buffer**.

Um buffer é como uma "caixa" ou uma "fila de espera" dentro do canal.

**Sintaxe de Criação:** `make(chan Tipo, capacidade)`

  * **`capacidade`:** O número de itens que o canal pode armazenar antes de bloquear.

<!-- end list -->

```go
// Cria um canal de inteiros com capacidade para 100 itens.
ch := make(chan int, 100)
```

**Comportamento:**

  * A goroutine que **envia** só irá bloquear se o buffer estiver **cheio**.
  * A goroutine que **recebe** só irá bloquear se o buffer estiver **vazio**.

**Exemplo Prático (da aula):**

```go
func main() {
	// O canal pode segurar até 100 inteiros.
	ch := make(chan int, 100)
	go setList(ch) // 'setList' é a mesma função de antes

	// A 'main' só começa a ler depois que 'setList' JÁ TERMINOU.
	for valor := range ch {
		fmt.Println("Recebido:", valor)
	}
	fmt.Println("Fim.")
}
```

**Saída (sem pausas):**

```
Enviando: 0
Enviando: 1
...
Enviando: 99
Produtor terminou de enviar.
Recebido: 0
Recebido: 1
...
Recebido: 99
Fim.
```

A `goroutine setList` conseguiu enviar todos os 100 itens para o buffer e terminar sua execução, tudo antes da `main` começar a consumir os itens. O buffer serviu como um "amortecedor", desacoplando o ritmo do produtor e do consumidor.

## 4\. Qual o Melhor? Bufferizado ou Não-Bufferizado?

Como a aula conclui, não existe "o melhor". A escolha depende do seu problema:

  * Use um **channel não-bufferizado** (`make(chan T)`) quando você precisa de uma **sincronização forte** e garantida entre o envio e o recebimento. É uma ótima ferramenta para sinalizar que um evento aconteceu.
  * Use um **channel com buffer** (`make(chan T, N)`) quando você quer **desacoplar** um produtor e um consumidor que trabalham em ritmos diferentes. É ideal para filas de trabalho (workers pools), onde um produtor gera tarefas e vários workers as consomem do buffer.
