# **8.2: Avançando com Generics - Type Constraints Customizadas**

Na aula anterior, aprendemos a usar Generics para escrever funções que operam sobre múltiplos tipos, definindo os tipos permitidos diretamente na assinatura da função (ex: `[T int | string]`). Nesta aula, exploramos uma técnica para tornar essas definições mais limpas, legíveis e reutilizáveis, especialmente quando lidamos com um grande número de tipos: as **constraints customizadas**.

## 1\. O Problema: Assinaturas de Funções Longas e Poluídas

Imagine que nossa função `Reverse` precise suportar não apenas `int` e `string`, mas também `float64`, e talvez alguns tipos customizados como `ClienteID`, `ProdutoID`, etc. A assinatura da nossa função começaria a ficar muito longa e difícil de ler:

```go
// Exemplo de uma assinatura de função genérica longa
func FuncaoComplexa[T int | string | float64 | Cliente | Produto | Categoria](param T) {
    // ...
}
```

Como a aula aponta, isso polui a assinatura da função, tornando a intenção do código menos clara à primeira vista.

## 2\. A Solução: Criando uma Constraint com `interface`

Para resolver isso, Go nos permite agrupar um conjunto de tipos permitidos em uma **constraint nomeada**. Fazemos isso usando a palavra-chave `type` para criar uma nova `interface`.

Esta não é uma interface de comportamento (com métodos), mas sim uma **interface de constraint de tipo**, onde listamos os tipos que a compõem, separados pelo operador `|` (OU).

**Sintaxe:**

```go
type NomeDaConstraint interface {
    Tipo1 | Tipo2 | Tipo3
}
```

**Aplicando ao nosso problema:**

```go
// Criamos uma constraint chamada 'TiposPermitidos'
type TiposPermitidos interface {
	int | string | float64 | Cliente | Produto | Categoria
}

// Agora, a assinatura da função fica muito mais limpa.
func FuncaoComplexa[T TiposPermitidos](param T) {
    // ...
}
```

Internamente, o resultado é o mesmo, mas a **legibilidade** do código melhora drasticamente. A assinatura da função agora expressa sua intenção de forma mais clara: "esta função opera sobre qualquer tipo que satisfaça a constraint `TiposPermitidos`".

## 3\. Exemplo Prático: Refatorando a Função `Reverse`

Vamos aplicar essa técnica à função `Reverse` da aula anterior para ver o efeito prático.

```go
package main

import "fmt"

// 1. Definimos nossa constraint customizada.
//    Qualquer tipo que seja int OU string satisfaz esta constraint.
type Reversible interface {
	int | string
}

// 2. Usamos a constraint nomeada 'Reversible' na assinatura da função.
func Reverse[T Reversible](s []T) []T {
	result := make([]T, len(s))
	for i := 0; i < len(s); i++ {
		result[len(s)-1-i] = s[i]
	}
	return result
}

func main() {
	// A chamada da função permanece exatamente a mesma.
	// O código continua funcionando perfeitamente.
	fmt.Println("Ints revertidos:", Reverse([]int{5, 1, 2, 3}))
	fmt.Println("Strings revertidas:", Reverse([]string{"a", "f", "o", "b"}))
}
```

## 4\. O "Go Way": Boas Práticas e Anti-Padrões

A aula termina com conselhos de engenharia de software muito importantes sobre o uso de Generics.

### a) Quando Criar uma Constraint Customizada?

Não existe uma regra rígida, é uma questão de bom senso e convenção de equipe. A recomendação da aula é um excelente ponto de partida:

  * **2-3 Tipos:** Escrevê-los diretamente na assinatura (`[T int | string]`) geralmente é aceitável e claro.
  * **Mais de 3 Tipos:** Considere fortemente criar uma constraint nomeada para não poluir a assinatura e melhorar a legibilidade.

### b) O Anti-Padrão: Generics para um Único Tipo

Um erro comum é usar a sintaxe de Generics para uma função que, na verdade, só suporta um único tipo.

**NÃO FAÇA ISTO (Anti-Padrão):**

```go
// Errado: Complexidade desnecessária
func FuncaoSoma[T int](a T, b T) T {
    return a + b
}
```

**Por quê?**

  * **Nenhum Benefício:** Você está adicionando a complexidade visual e cognitiva dos Generics sem obter nenhum dos seus benefícios (suporte a múltiplos tipos).
  * **Confuso:** Outros desenvolvedores que leem o código podem se perguntar por que a função é genérica se ela só funciona com `int`.

**FAÇA ISTO (Correto e Simples):**

```go
// Correto: Simples, direto e claro.
func FuncaoSoma(a int, b int) int {
    return a + b
}
```

A justificativa "vou deixar genérico para o futuro" geralmente é um sinal de **YAGNI (You Ain't Gonna Need It - Você não vai precisar disso)**, um princípio que desaconselha adicionar funcionalidades antes que elas sejam realmente necessárias. Escreva o código mais simples e claro para o problema que você está resolvendo *hoje*. Se no futuro a função precisar suportar `float64`, a refatoração para torná-la genérica é uma tarefa simples e rápida.
