# **6.7: Simulando herança em Go com Composição**

Se você vem de linguagens orientadas a objetos como Java ou C\#, está familiarizado com o conceito de **herança**, onde uma classe "filha" herda propriedades e comportamentos de uma classe "pai" (uma relação "é um").

Go, por design, **não possui herança clássica**. Em vez disso, ele incentiva um padrão mais flexível e explícito: a **composição**. A aula de hoje explora uma forma especial de composição que nos dá muitos dos benefícios da herança: o **Struct Embedding**.

## 1\. O Conceito: Herança ("É um") vs. Composição ("Tem um")

  * **Herança Clássica:** Um `Carro` **é um** `Automovel`. O `Carro` herda implicitamente todos os campos e métodos do `Automovel`.
  * **Composição em Go:** Um `Carro` **tem um** `Automovel`. A relação é explícita. O `Carro` contém uma instância de `Automovel` como um de seus campos.

## 2\. Modelando o Problema: `Automovel`, `Moto` e `Carro`

A aula constrói um exemplo perfeito para ilustrar o conceito. Temos características comuns a todos os automóveis e características específicas para cada tipo.

**`model/automovel.go`**

```go
package model

// Automovel contém os campos COMUNS a todos os automóveis.
type Automovel struct {
	Ano    int
	Placa  string
	Modelo string
}

// Moto tem seus campos ESPECÍFICOS...
type Moto struct {
	Automovel   // <-- Isto é Struct Embedding!
	Cilindradas int
}

// Carro tem seus campos ESPECÍFICOS...
type Carro struct {
	Automovel         // <-- Isto é Struct Embedding!
	QuantidadePortas  int
	Potencia          int
	PossuiArCondicionado bool
}
```

## 3\. A Diferença Crucial: Composição Padrão vs. Struct Embedding

Aqui está a chave de toda a aula. A sintaxe que usamos para incluir uma `struct` dentro de outra muda drasticamente como acessamos seus campos.

### a) Composição Padrão (Campo Nomeado)

Se déssemos um nome ao campo `Automovel`, teríamos a composição padrão que já vimos.

```go
// Composição Padrão
type Moto struct {
    InfoGerais Automovel // Campo nomeado 'InfoGerais'
    Cilindradas int
}

// Para acessar o ano, precisaríamos do caminho completo:
// minhaMoto.InfoGerais.Ano
```

### b) Struct Embedding (Campo Anônimo)

Ao incluir o tipo `Automovel` diretamente na `struct Moto` **sem dar um nome ao campo**, estamos usando **embedding**.

```go
// Struct Embedding
type Moto struct {
    Automovel // Campo anônimo (o nome do tipo é usado implicitamente)
    Cilindradas int
}
```

**A "Mágica" do Embedding:** Go **promove** os campos e métodos do tipo embutido (`Automovel`) para o tipo externo (`Moto`). Isso significa que você pode acessá-los diretamente, como se pertencessem à `Moto`.

## 4\. O Embedding na Prática

Vamos ver como isso funciona no nosso `main.go`.

```go
// main.go
package main

import (
	"fmt"
	"golang-estudo/model"
)

func main() {
	// 1. Criamos uma moto
	minhaMoto := model.Moto{
		Cilindradas: 125,
		Automovel: model.Automovel{ // Ainda inicializamos o tipo embutido
			Ano:    2022,
			Placa:  "XPT-1234",
			Modelo: "CG",
		},
	}
	fmt.Printf("Moto: %+v\n", minhaMoto)

	// 2. Acessando os campos
	fmt.Println("\n--- Acessando Campos ---")
	
	// Acessando o campo da própria Moto
	fmt.Println("Cilindradas:", minhaMoto.Cilindradas)
	
	// Acessando os campos PROMOVIDOS de Automovel DIRETAMENTE!
	fmt.Println("Ano da Moto:", minhaMoto.Ano)
	fmt.Println("Placa da Moto:", minhaMoto.Placa)
	
	// O tipo interno ainda é acessível se precisarmos
	fmt.Println("Modelo (via acesso explícito):", minhaMoto.Automovel.Modelo)
}
```

**Saída:**

```
Moto: {Automovel:{Ano:2022 Placa:XPT-1234 Modelo:CG} Cilindradas:125}

--- Acessando Campos ---
Cilindradas: 125
Ano da Moto: 2022
Placa da Moto: XPT-1234
Modelo (via acesso explícito): CG
```

Observe como pudemos chamar `minhaMoto.Ano` em vez de `minhaMoto.Automovel.Ano`. Este é o benefício de legibilidade e conveniência do embedding.

## 5\. "Herança" de Comportamento: Promoção de Métodos

A promoção não se aplica apenas aos campos, mas também aos **métodos**. Se definirmos um método no tipo `Automovel`, os tipos `Moto` e `Carro` automaticamente "herdarão" esse comportamento.

**`model/automovel.go` (com um método)**

```go
// ... (definições das structs)

func (a Automovel) LigarMotor() string {
	return fmt.Sprintf("O motor do modelo %s (%d) foi ligado.", a.Modelo, a.Ano)
}
```

**`main.go` (usando o método promovido)**

```go
// (continuação da função main)
fmt.Println("\n--- Usando Método Promovido ---")
fmt.Println(minhaMoto.LigarMotor()) // O método de Automovel é chamado em Moto!
```

**Saída:**

```
--- Usando Método Promovido ---
O motor do modelo CG (2022) foi ligado.
```

## 6\. O "Go Way": Por que Usar Embedding?

  * **Reutilização de Código:** Evita que você precise redefinir campos comuns (`Ano`, `Placa`, `Modelo`) em todas as suas `structs`.
  * **Comportamento Compartilhado:** Permite que múltiplos tipos compartilhem métodos definidos em uma `struct` base. Pense em campos como `ID`, `CreatedAt`, `UpdatedAt` com métodos de validação ou formatação.
  * **Clareza:** Embora seja uma forma de composição, a sintaxe de acesso direto (`objeto.CampoPromovido`) torna o código mais limpo e próximo da experiência de herança.
  * **Implicações em Ferramentas:** Como a aula mencionou, ferramentas como ORMs (Object-Relational Mappers) e serializadores (JSON) geralmente entendem o embedding e "achatam" a estrutura, o que pode ser muito útil para mapear para uma única tabela de banco de dados, por exemplo.
