# **7.2: Praticando Interfaces - O Tipo `error`**

Nesta aula, vamos solidificar nosso entendimento sobre interfaces trabalhando com a interface mais comum em todo o ecossistema Go: a interface `error`. Este exercício prático demonstrará por que programar para "comportamentos" (abstrações) é muito mais poderoso do que programar para "tipos" (implementações concretas).

## 1\. A Interface `error` Nativa do Go

Go tem uma interface nativa extremamente simples, definida no próprio núcleo da linguagem, para representar erros.

Sua definição é a seguinte:

```go
type error interface {
    Error() string
}
```

**O Contrato:** Qualquer tipo de dado, não importa qual seja sua estrutura, que possua um método chamado `Error` (com 'E' maiúsculo) que não recebe argumentos e retorna uma `string`, é, por definição, um `error`. Ele satisfaz a interface `error` implicitamente.

## 2\. Criando Erros Simples com o Pacote `errors`

A forma mais fácil de criar um valor que satisfaça essa interface é usando a função `errors.New` do pacote `errors`.

```go
package main

import (
	"errors"
	"fmt"
)

func main() {
    // errors.New cria um tipo de erro simples que contém apenas uma mensagem de texto.
	err := errors.New("um erro de teste ocorreu")
	
    // 'err' agora é uma variável que satisfaz a interface 'error'.
	fmt.Println(err.Error()) // Chamando o método do contrato
}
```

## 3\. O Poder das Interfaces: Funções Abstratas

Agora, vamos criar uma função que trabalha com a **abstração** (a interface `error`), não com um tipo concreto.

```go
// Esta função não sabe qual tipo de erro vai receber.
// Ela só sabe que, seja o que for, TERÁ um método .Error() string.
func exibeErro(e error) {
	fmt.Println("Ocorreu um erro:", e.Error())
}

func main() {
	errSimples := errors.New("um erro de teste ocorreu")
	exibeErro(errSimples) // Funciona perfeitamente.
}
```

## 4\. O Salto Conceitual: Criando Tipos de Erro Customizados

E se um simples texto não for suficiente? E se quisermos que nosso erro carregue mais informações, como um código de status, se o problema foi de rede ou de hardware, etc.?

É aqui que o poder das interfaces brilha. Podemos criar nossa própria `struct` para conter esses dados ricos e, em seguida, fazer com que ela **cumpra o contrato da interface `error`**.

### a) Definindo a Struct Customizada

```go
// ProblemaDeNetwork é uma struct que carrega informações detalhadas sobre um erro.
type ProblemaDeNetwork struct {
	ProblemaDeRede     bool
	ProblemaDeHardware bool
}
```

### b) Implementando a Interface `error`

Para que um `ProblemaDeNetwork` possa ser usado onde um `error` é esperado, ele precisa ter um método `Error() string`.

```go
// Ao adicionar este método, ProblemaDeNetwork agora satisfaz a interface 'error'.
func (p ProblemaDeNetwork) Error() string {
	if p.ProblemaDeRede {
		return "Um problema de rede ocorreu."
	}
	if p.ProblemaDeHardware {
		return "Um problema de hardware ocorreu."
	}
	return "Um problema desconhecido ocorreu."
}
```

## 5\. O Resultado Final: Flexibilidade e Desacoplamento

Agora, a nossa função `exibeErro`, que não foi alterada e não sabe nada sobre `ProblemaDeNetwork`, pode aceitar nosso novo tipo de erro customizado.

```go
// (função exibeErro permanece a mesma)
func exibeErro(e error) {
	fmt.Println("Ocorreu um erro:", e.Error())
}

func main() {
    // --- Cenário 1: Erro simples ---
	errSimples := errors.New("falha ao conectar na API")
	exibeErro(errSimples)

    // --- Cenário 2: Erro customizado e rico em detalhes ---
	errCustomizado := ProblemaDeNetwork{
		ProblemaDeRede: true, // O problema foi de rede
	}
	// Podemos passar nossa struct customizada para a MESMA função!
	exibeErro(errCustomizado) 
}
```

**Saída:**

```
Ocorreu um erro: falha ao conectar na API
Ocorreu um erro: Um problema de rede ocorreu.
```

## 6\. O "Go Way": Abstração vs. Concretude

Esta aula demonstra um dos princípios mais importantes da engenharia de software, que é central em Go: **"Programe para uma interface, não para uma implementação."**

| Código Acoplado (Ruim) | Código Desacoplado (Bom) |
| :--- | :--- |
| `func exibeErroDeRede(p ProblemaDeNetwork)` | `func exibeErro(e error)` |
| `func exibeErroSimples(e errorString)` | |
| **Problema:** Você precisa de uma função para cada tipo concreto de erro. | **Vantagem:** Uma única função pode lidar com qualquer tipo de erro presente ou futuro, desde que ele cumpra o contrato da interface `error`. |

Como o instrutor enfatizou, a função `exibeErro` **não recebe uma implementação concreta**, ela recebe uma **abstração**. Ela não se importa se o erro veio do `errors.New` ou da nossa `struct` customizada. Ela só se importa que o valor recebido saiba como se comportar como um erro (ou seja, que tenha o método `Error() string`). Isso torna nosso código imensamente mais flexível e extensível.
